# Videotape — Design Specification, v1

**Date:** 2026-10-22 · **Status:** draft, ready to build against · **Companions:**
[01-review-and-risks.md](01-review-and-risks.md), [03-landscape.md](03-landscape.md)

Videotape is a framework in which a user interface is authored as **tapes** (user journeys) made of
**frames** (still states), rendered as **generated video** by an **engine**, and displayed by a thin
**player** that knows which regions of the picture are interactive.

This document specifies the first version: what it does, how the pieces fit, the contracts between
them, and the order to build them in. Decisions are stated with their reasons so they can be revisited.

---

## 0. Scope of v1 in one paragraph

v1 is a working framework plus a public demo. A developer writes tapes in TypeScript, runs one
command, and gets a browser player that shows their app at any screen size. The scene behind every
frame is generated by an image model conditioned on the frame's layout; transitions between frames
are generated by a video model; every piece of text, data, and input is rendered natively on top
so it is always correct and always operable. The whole system also runs with the AI switched off,
which is how it is tested. Real-time whole-screen video is defined as a plugin interface, with
implementation as a stretch goal.

---

## 1. Goals, non-goals, success criteria

### 1.1 Goals
- **G1** Author a UI as tapes of frames in TypeScript with no layout or styling code.
- **G2** Play it in a browser at any viewport with native interaction (typing, focus, keyboard,
  screen readers).
- **G3** Generate the scene layer of each frame with a model conditioned on the layout; generate
  transitions between frames.
- **G4** Run end to end with the AI switched off (deterministic renderer), in CI.
- **G5** Keep every model behind a renderer plugin; no vendor SDK is imported outside `renderers/`.
- **G6** Cache everything generated, content-addressed: same inputs produce the same picture.

### 1.2 Non-goals for v1
- **N1** Real-time per-pixel generation of the whole screen for every user (interface only).
- **N2** Native mobile or desktop players. A Mac shell, if built, is a thin web wrapper.
- **N3** A visual authoring tool ("Studio").
- **N4** On-device generation.
- **N5** Accounts, persistence beyond the session, multi-user. The demo uses fake auth.
- **N6** Burning facts (text, data) into the video on the server.
- **N7** Long scrolling pages. A frame is one screen; list archetypes scroll inside a region.

### 1.3 Success criteria (the demo must show all of these)
- **S1** The demo app (landing → docs → login → dashboard → report) is defined in at most ~120 lines
  of tape code.
- **S2** Every interactive component is a native DOM element: typing, focus order, Enter/Escape,
  screen-reader labels all work.
- **S3** At least three frames have generated scene layers; the same cache key yields a
  byte-identical asset.
- **S4** At least two edges have generated cuts. When prefetched, p95 click-to-next-frame is at or
  under 300 ms. When not, a crossfade plays. A spinner never appears.
- **S5** CI runs the full loop with the flat renderer and walks every edge of the demo graph.
- **S6** `videotape check` reports unreachable frames, dangling jumps, and interactive components
  without a handler.
- **S7** The demo is deployed at a public URL and a stranger can define a tape and see it.

## 2. Vocabulary

| Term | Meaning |
|------|---------|
| **Tape** | An ordered sequence of frames: one user journey. Has an id, an entry frame, and a style. |
| **Frame** | One still state of the UI, one screen. Declares a scene, a layout, components, and handlers. |
| **Component** | A typed element in a frame (text, button, input, …). Interactive or not. |
| **Slot** | A named position in a layout archetype that a component occupies. |
| **Archetype** | A layout family: `hero`, `form`, `list`, `detail`, `grid`, `reader`, `blank`. |
| **Viewport class** | A bucket of screen sizes with a canonical canvas (`phone`, `tablet`, `desktop`). |
| **Wireframe** | Layout engine output: regions with rectangles, roles, and masks. Emitted as JSON and SVG. |
| **Scene** | The generated layer behind the content. Described by a prompt plus a style pack. |
| **Style pack** | Seed, palette, typography tokens, reference images, prompt prefix/suffix, optional LoRA. |
| **Cut** | A transition along an edge between two frames. Generated video or a deterministic crossfade. |
| **Ambient** | Optional looping motion for a frame's scene. |
| **Edge** | A (frame, event) → frame transition. The set of edges is the app's graph. |
| **Head** | The player's current position: (tape, frame). |
| **Reel** | One session: head, history stack, data store, viewport. |
| **Render** | The deliverable for one frame at one viewport class: scene assets, wireframe, content-layer spec, edges, a11y. |
| **Renderer** | A plugin that produces scene assets or cuts. Kinds: `flat`, `still`, `cut`, `live`. |
| **Engine** | The server: sessions, pipeline, cache, protocol. |
| **Player** | The browser client. |
| **VTP** | Videotape Protocol: the WebSocket message set between player and engine. |

## 3. Principles

1. **Journey first.** The tape graph is the program. Everything else hangs off it.
2. **Form from the model, facts from the code, space from the layout.** The generator never renders
   a fact. The layout engine decides every region before a pixel is generated.
3. **Works with the AI off.** The `flat` renderer is a first-class renderer, not a mock.
4. **Same inputs, same picture.** Every generated asset is content-addressed and cached. The cache is
   what makes an app look like itself.
5. **Native where it matters.** Inputs, text, and focus are real DOM. The picture is behind them.
6. **No pixel-derived interactivity.** Hit regions come from the spec, never from the image.
7. **Pluggable renderers.** Models are plugins. The engine does not know which model is in use.
8. **Budgets, not spinners.** Every wait has a budget and a deterministic fallback.
9. **The ratchet.** Move one more category from deterministic to generated per milestone, measured
   as the share of screen area that is generated, reversible per frame.

## 4. Architecture

```
┌──────────────────────────────┐    VTP/1 over WebSocket (JSON)     ┌────────────────────────────────┐
│ PLAYER  (browser, full view) │ ◄───────────────────────────────► │ ENGINE  (server)               │
│  z3 hud      (debug only)    │  hello · welcome · render · cut    │  sessions (reels)              │
│  z2 content  (DOM: text,     │  event · patch · prefetch · resize │  pipeline: resolve → layout →  │
│              inputs, buttons)│                                    │    plan → generate → validate  │
│  z1 cut      (<video>)       │   assets over HTTPS, immutable,    │    → cache → deliver           │
│  z0 scene    (<img>/<video>) │ ◄──────── content-addressed ────── │  renderer host                 │
└──────────────────────────────┘                                    │   flat · still · cut · live    │
                                                                    └───────────────┬────────────────┘
                                                                                    │ imports
                                                                    ┌───────────────┴────────────────┐
                                                                    │ APP  (tapes, handlers, services)│
                                                                    │  built on @videotape/core      │
                                                                    └────────────────────────────────┘
```

**Packages** (see §12 for the tree):

- `@videotape/core` — the model (tapes, frames, components), schemas, validation, graph, and the
  layout engine. Pure functions, no I/O, no model calls. Everything else depends on it.
- `@videotape/engine` — sessions, the render pipeline, cache, the VTP server, the renderer host.
- `@videotape/player` — the browser client.
- `@videotape/renderer-*` — one package per renderer backend.
- `@videotape/cli` — `videotape dev | check | graph | render | serve`.
- `apps/site` — the demo app and the public site.

**Request lifecycle** (happy path, cached):

1. Player opens the page, measures the viewport, sends `hello`.
2. Engine creates a reel at the app's entry tape and frame, snaps the viewport to a class, sends
   `welcome`.
3. Engine resolves the frame, runs layout, computes the cache key, finds the scene asset in cache,
   sends `render`.
4. Player shows the scene, mounts the content layer from the render spec, and prefetches assets for
   every outgoing edge listed in `render.edges`.
5. User presses "Sign in". Player shows pressed state immediately, sends `event`.
6. Engine validates the event against the frame, runs the handler, gets `jump("dashboard")`,
   resolves the target frame, finds the cut and scene in cache, sends `cut` then `render`.
7. Player plays the cut video over the old scene, swaps to the new scene on the last frame, mounts
   the new content layer.

On a cache miss at step 3 or 6, the engine generates (§7), and the player receives a `flat` render
immediately if the budget would otherwise be exceeded, followed by a `patch` when the generated
asset is ready.

## 5. The tape model

### 5.1 Authoring API (TypeScript)

```ts
import { tape, frame, text, input, button, link, list, image,
         goto, jump, back, stay, bind, handler } from "@videotape/core";

export const login = tape("login", {
  title: "Sign in",
  style: "dusk",                       // style pack id, see §7.4
  frames: [
    frame("form", {
      layout: "form",
      scene: "A quiet sign-in moment for Videotape. Dusk gradient, a faint cassette silhouette, " +
             "soft volumetric light, generous negative space, cinematic.",
      components: [
        text("title", "Welcome back", { slot: "form.title", variant: "title" }),
        input("username", { label: "Username", slot: "form.field.1" }),
        input("password", { label: "Password", type: "secret", slot: "form.field.2" }),
        text("error", bind("login.error"), { slot: "form.error", variant: "caption" }),
        button("submit", "Sign in", { slot: "form.primary", on: { press: "submit" } }),
        link("forgot", "Forgot password?", { slot: "form.secondary", on: { press: jump("reset") } }),
      ],
      on: {
        submit: handler(
          async ({ values, services }) => {
            const user = await services.auth.login(values.username, values.password);
            return user ? jump("dashboard", { user }) : stay({ "login.error": "Wrong credentials" });
          },
          { outcomes: [jump("dashboard"), stay()] },   // declared so the graph knows the edges
        ),
      },
    }),
  ],
});
```

Rules the API enforces or lints:

- A component's `on.press` is either a **static action** (`goto`, `jump`, `back`) or the **name of a
  frame handler**. Static actions are edges the graph knows. Handlers declare their possible
  `outcomes` so the graph knows those edges too; a handler without `outcomes` produces a warning in
  `videotape check` and its edges are not prefetched.
- `scene` is a string, or a function of **flavour** only (§5.5). It never receives reel data.
- Every `bind()` reads a path in the reel's data store and is rendered on the content layer.
- An input-like component (`input`, `textarea`, `select`, `toggle`, `slider`, `date`) may take
  `bind: "path"`. Its value is then read from the store when the frame renders and written to that
  path when the value is committed. A `secret` input cannot be bound.
- A frame may declare `enter: async ({ data, services, reel }) => patch | void`. It runs on the
  server each time the head arrives at the frame (by `goto`, `jump`, `back`, or as the app's
  entry), before the frame renders, and its patch is merged into the store. It cannot move the head,
  so the graph stays static. This is how a frame loads the data it binds.

### 5.2 Semantics

- **Head movement.** `goto(frameId)` moves within the current tape. `jump(tapeId, data?)` switches
  tape, pushes the previous head on the reel's history stack, and merges `data` into the store.
  `back()` pops the stack. `stay(patch?)` keeps the head and patches the data store; the player
  receives a `patch`, not a new render.
- **Handlers run on the server.** They are app code with access to `values` (committed component
  values for this event), `data` (the reel store), `services` (whatever the app injects), and
  `reel` (head, history, viewport class). They return an outcome.
- **Events.** Each component kind emits a fixed set of events (§5.3). The engine drops any event
  that the current frame does not declare, and logs it.
- **Entry.** Each tape has an entry frame (default: its first). The app declares an entry tape.
- **Data store.** A JSON object scoped to the reel. Values marked `secret` are passed to the handler
  once and never stored.
- **Patches.** The data passed to `jump`, the patch passed to `stay`, and the value an `enter` hook
  returns are all maps of **path → value** (`{ "login.error": "Wrong credentials" }`). Each entry
  replaces the value at its path; missing parents are created.
- **Handler context.** `values` holds committed values keyed by component id. For a `list`
  `select` event it also holds `item`, the selected item's id.

### 5.3 Component kinds

| Kind | Interactive | Events | Notes |
|------|-------------|--------|-------|
| `text` | no | — | `variant`: title, subtitle, body, caption, number. Value may be `bind()`. |
| `image` | no | — | `src` is an app asset URL or `bind()`. Never generated. |
| `media` | no | — | Video or audio URL. Native element. |
| `button` | yes | `press` | `emphasis`: primary, secondary. |
| `link` | yes | `press` | Inline or nav link. |
| `input` | yes | `change`, `commit` | `type`: text, secret, email, number, search. `commit`: `submit` (default), `blur`, `change`. |
| `textarea` | yes | `change`, `commit` | Multi-line. |
| `select` | yes | `change` | Options are static or `bind()`. |
| `toggle` | yes | `change` | Boolean. |
| `slider` | yes | `change`, `commit` | Numeric range. |
| `date` | yes | `change` | Native date input. |
| `list` | yes (items) | `select` | Items from `bind()`; each item renders a label and optional meta; `select` carries the item id. |

Every component has `id`, optional `slot`, optional `a11y: { label, role }`. The engine derives
`interactive` from the kind.

### 5.4 Wire format

Tapes are defined in TypeScript and serialised to JSON for the engine, the CLI, and the player.
Schemas are defined once in Zod in `@videotape/core` and exported as JSON Schema. Abbreviated:

```json
{
  "id": "login",
  "title": "Sign in",
  "style": "dusk",
  "entry": "form",
  "frames": [{
    "id": "form",
    "layout": "form",
    "scene": "A quiet sign-in moment …",
    "components": [
      { "id": "title",    "kind": "text",   "slot": "form.title",   "variant": "title", "value": "Welcome back" },
      { "id": "username", "kind": "input",  "slot": "form.field.1", "label": "Username" },
      { "id": "password", "kind": "input",  "slot": "form.field.2", "label": "Password", "type": "secret" },
      { "id": "error",    "kind": "text",   "slot": "form.error",   "variant": "caption", "bind": "login.error" },
      { "id": "submit",   "kind": "button", "slot": "form.primary", "label": "Sign in", "on": { "press": "submit" } },
      { "id": "forgot",   "kind": "link",   "slot": "form.secondary", "label": "Forgot password?",
        "on": { "press": { "type": "jump", "tape": "reset" } } }
    ],
    "on": { "submit": { "outcomes": [ { "type": "jump", "tape": "dashboard" }, { "type": "stay" } ] } }
  }]
}
```

Handler bodies are not serialised; the JSON carries only their declared outcomes.

### 5.5 Scene authoring rules

- `scene` is static text, or a function `(flavour) => string`.
- **Flavour** is a small, explicit projection of reel data that the frame declares:
  `flavour: (data) => ({ weather: data.forecast.kind })`. It exists so that mood can follow data
  ("rainy day") without user-entered text ever reaching a prompt. The projection is the single
  place reviewers look.
- The engine composes the final prompt as `style.prefix + scene + layout hints + style.suffix`.
  Layout hints are generated from the wireframe ("a calm, untextured panel in the centre third").
- Lint: `videotape check` warns when a `scene` function reads a path that any `input` in the app
  writes to.

### 5.6 Validation (`videotape check`)

Errors: duplicate ids; `goto` to an unknown frame; `jump` to an unknown tape; a slot that the
archetype does not define; an interactive component with no action and no handler; a handler named
in `on.press` that the frame does not define; a `bind()` to a secret value.
Warnings: unreachable frames; handlers without `outcomes`; frames with no exit; cycles with no exit;
scene functions that read input-written paths; more than one `primary` button in a frame.

## 6. Layout

The layout engine is a pure function in `@videotape/core`:
`layout(frame, viewportClass, style) → Wireframe`. It is snapshot-tested and never calls a model.

### 6.1 Viewport classes

| Class | Trigger (CSS px) | Canonical canvas | Aspect |
|-------|------------------|------------------|--------|
| `phone` | width < 600 | 1080 × 1920 | 9:16 |
| `tablet` | 600 ≤ width < 1024 | 1536 × 2048 | 3:4 |
| `desktop` | width ≥ 1024 | 1920 × 1080 | 16:9 |

Scene assets are generated at the canonical canvas. The player scales the picture to **cover** the
viewport and applies the same transform to the content layer, so regions stay aligned. A **safe
area** of 6 % on each side keeps every region visible under cover-cropping. `wide` and `tv` classes
are reserved for later.

Cover alone is not enough: a common 390 × 844 phone is narrower than 9:16 and would crop about 9 %
from each side, past the safe area. The player therefore covers only when the crop stays inside
the safe margin; otherwise it shrinks the stage until the safe area plus a small gutter (4.5 % of
the canvas per side) is visible. The stage is centred and the uncovered edges show a blurred,
enlarged copy of the scene, so no region is ever cut off or flush with the window edge.

### 6.2 Archetypes and slots

| Archetype | Slots | Use |
|-----------|-------|-----|
| `hero` | `nav.leading`, `nav.trailing`, `hero.title`, `hero.subtitle`, `hero.primary`, `hero.secondary`, `hero.media`, `footer` | Landing, marketing, empty states. |
| `form` | `nav.leading`, `form.title`, `form.field.N`, `form.error`, `form.primary`, `form.secondary`, `form.aside` | Sign in, settings, any data entry. |
| `list` | `nav.leading`, `nav.trailing`, `list.title`, `list.search`, `list.items`, `list.primary` | Feeds, inboxes, catalogues. |
| `detail` | `nav.leading`, `nav.trailing`, `detail.title`, `detail.media`, `detail.body`, `detail.meta`, `detail.primary`, `detail.secondary` | One item, one report. |
| `grid` | `nav.leading`, `nav.trailing`, `grid.title`, `grid.cell.N`, `grid.aside` | Dashboards. |
| `reader` | `nav.leading`, `reader.title`, `reader.body`, `reader.toc` | Docs, articles. |
| `blank` | free: each component gives `rect: [x, y, w, h]` in canvas fractions | Escape hatch. |

Each archetype has one rule set per viewport class (for example, `form.aside` collapses on `phone`;
`grid.cell.N` is one column on `phone`, two on `tablet`, up to four on `desktop`). Components without
a slot are auto-placed in declaration order into the archetype's default sequence. If a frame gives
no `layout`, the engine infers one: inputs present → `form`; a `list` → `list`; many `number` texts
→ `grid`; otherwise `hero`.

### 6.3 Output: the wireframe

```json
{
  "canvas": { "w": 1920, "h": 1080 },
  "safe":   [0.06, 0.06, 0.88, 0.88],
  "regions": [
    { "id": "title",    "kind": "text",   "rect": [0.35, 0.28, 0.30, 0.08], "mask": "reserved", "z": 2 },
    { "id": "username", "kind": "input",  "rect": [0.35, 0.42, 0.30, 0.06], "mask": "reserved", "z": 2 },
    { "id": "password", "kind": "input",  "rect": [0.35, 0.50, 0.30, 0.06], "mask": "reserved", "z": 2 },
    { "id": "submit",   "kind": "button", "rect": [0.35, 0.60, 0.30, 0.06], "mask": "surface",  "z": 2 },
    { "id": "forgot",   "kind": "link",   "rect": [0.35, 0.68, 0.30, 0.04], "mask": "reserved", "z": 2 },
    { "id": "__panel",  "kind": "panel",  "rect": [0.31, 0.22, 0.38, 0.54], "mask": "surface",  "z": 1 }
  ],
  "svg": "<svg …>…</svg>"
}
```

Rectangles are `[x, y, w, h]` as fractions of the canonical canvas. Masks:

- `reserved` — the generator must keep this calm: low texture, enough contrast against the style's
  foreground colour. Text and inputs live here.
- `surface` — the generator may draw chrome here (a button face, a card, a panel). The content layer
  places only the label and an invisible hit target on top.
- everything else — free.

The `svg` is the wireframe drawn with the style palette: panels as rounded rectangles, fields as
lighter strips, buttons as filled shapes, text as grey bars. It is the `flat` renderer's input and
the `still` renderer's conditioning image.

## 7. Engine pipeline

### 7.1 Steps

| Step | Input → Output | Where |
|------|----------------|-------|
| `resolve` | reel → frame, data, flavour | engine |
| `layout` | frame, viewport class, style → wireframe | core |
| `plan` | frame, wireframe, style, flavour → render plan (scene key and prompt, condition image, masks, cut keys for each outgoing edge) | engine |
| `generate` | plan → scene asset, cut assets; cache first | renderer host |
| `validate` | asset, wireframe → pass, or re-roll, or per-region flat patch | engine |
| `cache` | key, asset → stored, content-addressed | engine |
| `deliver` | render message; schedule prefetch for outgoing edges | engine |

### 7.2 Cache key

```
key = sha256(core.version, renderer.id, renderer.version,
             frame.specHash,            // scene text, layout, components (ids, kinds, slots, static labels)
             viewportClass, style.id, style.seed, flavourHash)
```

Reel **data is not part of the key**: facts live on the content layer, so one scene asset serves
every user. The cache is a content-addressed store with a filesystem implementation and an S3-style
adapter. A manifest maps keys to asset hashes so re-rolls can coexist and one can later be pinned.

### 7.3 Validation and re-roll

For each `reserved` region: luminance variance below a threshold, and contrast between the region's
mean colour and the style's foreground colour at or above 4.5:1 (WCAG AA). For each `surface` region:
nothing enforced in v1. A failing asset is re-rolled with the next seed up to three times; if it
still fails, the engine composites a flat fill from the style palette into the failing regions only
and keeps the rest. The HUD shows re-roll and patch counts per frame.

### 7.4 Style packs

A style pack is a small JSON file in the app:

```json
{
  "id": "dusk",
  "seed": 4210,
  "palette": { "bg": "#14121a", "fg": "#f3ede4", "accent": "#ff6a3d", "muted": "#8a8494" },
  "fonts":   { "display": "Instrument Serif", "body": "Inter" },
  "prompt":  { "prefix": "Cinematic UI backdrop, ", "suffix": ", film grain, 35mm, no text, no letters" },
  "references": ["styles/dusk/ref-1.png"],
  "lora": null
}
```

Palette and fonts drive the content layer and the wireframe. Prefix, suffix, references, and LoRA
drive the generator. "no text, no letters" belongs in every suffix.

### 7.5 Prefetch and budgets

After delivering a render, the engine queues, in order: the scene assets of every outgoing edge's
target frame; the cuts for those edges; ambient loops if enabled. The player receives `prefetch`
messages and warms its cache. Budgets:

| Wait | Budget | Fallback |
|------|--------|----------|
| First render of a session | 1.5 s | `flat` render, then `patch` when generated asset lands |
| Click → next frame (prefetched) | 300 ms | — |
| Click → next frame (not prefetched) | 300 ms | crossfade to `flat` render, then `patch` |
| Cut playback | 0.6–1.2 s | crossfade |

### 7.6 Renderer plugin interface

```ts
export interface SceneRenderer {
  id: string; version: string; kind: "scene";
  render(req: SceneRequest, signal: AbortSignal): Promise<SceneAsset>;
}
export interface CutRenderer {
  id: string; version: string; kind: "cut";
  render(req: CutRequest, signal: AbortSignal): Promise<CutAsset>;
}
export interface LiveRenderer {                       // v1: interface only
  id: string; version: string; kind: "live";
  open(session: LiveSession): LiveStream;             // WebRTC track in, WebRTC track out
}

export interface SceneRequest {
  key: string; canvas: { w: number; h: number }; seed: number;
  prompt: string; negative?: string;
  condition: { svg: string; png: Uint8Array };        // the wireframe
  masks: { reserved: Uint8Array; surface: Uint8Array };
  style: StylePack;
}
export interface CutRequest {
  key: string; canvas: { w: number; h: number }; seed: number;
  from: SceneAsset; to: SceneAsset; prompt: string; durationMs: number;
}
export interface SceneAsset { key: string; mime: "image/webp" | "image/png"; bytes: Uint8Array; meta: Record<string, unknown>; }
export interface CutAsset   { key: string; mime: "video/webm" | "video/mp4";  bytes: Uint8Array; durationMs: number; meta: Record<string, unknown>; }
```

### 7.7 Renderers in v1

| Renderer | Package | What it does | Backend |
|----------|---------|--------------|---------|
| `flat` | `renderer-flat` | Rasterises the wireframe SVG with the style palette. Reference renderer; always available; used in CI and as every fallback. | `@resvg/resvg-js` |
| `still` | `renderer-still-fal` | Layout-conditioned image generation: an image model with structural conditioning (canny/depth/segmentation control, or image-to-image over the wireframe raster at low denoise) plus the composed prompt. | fal.ai hosted models; exact model ids are chosen at implementation time and recorded in `03-landscape.md`. |
| `still` | `renderer-still-comfy` | Same contract against a local ComfyUI workflow (SDXL or FLUX with a ControlNet). Open-weights path. | ComfyUI HTTP API |
| `cut` | `renderer-cut-fal` | First-and-last-frame video between two scene assets. | fal.ai (LTX-2.x family first-last-frame endpoint) |
| `cut` | `renderer-cut-comfy` | Same against local LTX-2.x or Wan 2.x first-last-frame workflows. | ComfyUI HTTP API |
| `live` | `renderer-live-decart` (stretch) | Real-time video-to-video: the engine streams the `flat` render as the input video, the model restyles it live, the player shows the output under the content layer. The input stream is the layout conditioning. | Decart Realtime API over WebRTC |

The `live` design is worth noting: real-time video-to-video models take a video *in*, which means
the flat render can be the conditioning signal frame by frame. That is the same "form from the
model, facts from the code" split, just at 30 fps.

---

## 8. Player

- **Form.** One HTML page, one script, no framework. Target under 50 KB gzipped. Vite build.
- **Layers** (z-order): `scene` (an `<img>` or looping `<video>`), `cut` (a `<video>` shown only
  during a transition), `content` (absolutely positioned DOM nodes from `render.content`), `hud`
  (debug only).
- **Scaling.** A container with the canonical canvas aspect is scaled to cover the viewport. Regions
  are positioned in percentages; type sizes use container-relative units so text stays crisp.
- **Lifecycle.** connect → `hello` → `welcome` → `render` → mount content → prefetch → … →
  user event → optimistic state → `event` → `cut` (play over old scene) → `render` (swap scene on
  the cut's last frame, remount content with a 120 ms fade) → prefetch.
- **Input.** Pointer and keyboard events are handled by the content nodes only. Tab order follows
  slot order. Enter in a form input triggers the frame's primary button. Escape sends `back` if the
  frame allows it. There is no pixel hit-testing anywhere.
- **Button faces.** In v1 the content layer draws button faces natively (accent for primary). §7.3
  enforces nothing on `surface` regions yet, so a generated scene cannot be trusted to draw an
  affordance under every label; the face moves to the generator in the ratchet step that adds
  surface validation. The flat scene therefore draws only panels and media frames.
- **Immediate feedback.** Focus ring, caret, typing, pressed state, and disabled-during-transition
  are all local and instant. A transition in flight disables the content layer with a 2 s timeout
  that re-enables it and shows the fallback.
- **Resize.** Debounced 150 ms. A viewport class change sends `resize` and expects a new render.
  Within a class, only CSS changes.
- **Degradation.** Connection lost: keep the last picture, disable content, show a small badge,
  reconnect with backoff and `hello.resume`. Render failure: the engine sends a `flat` render.
- **Mobile.** `100dvh`, viewport meta, real inputs so the IME behaves, input font size at or above
  16 px to prevent zoom-on-focus, touch targets at or above 44 px.
- **HUD** (`?debug=1` or the backtick key): region outlines with mask colours, current head, cache
  hit/miss per asset, timings for the last transition, outgoing edges and their prefetch state.

## 9. Protocol: VTP/1

JSON messages over one WebSocket. Binary assets are fetched over HTTPS from content-addressed URLs
(`/a/<sha256>.<ext>`) with immutable cache headers.

| Direction | Message | Fields |
|-----------|---------|--------|
| C→S | `hello` | `v: 1`, `viewport: {w, h, dpr}`, `caps: {video: ["webm","mp4"], webrtc: bool}`, `resume?: token` |
| S→C | `welcome` | `session`, `token`, `viewportClass`, `canvas`, `style` (palette, fonts) |
| S→C | `render` | `seq`, `head`, `canvas` (changes with the viewport class), `key`, `layers[]`, `regions[]`, `content[]`, `edges[]`, `a11y`, `fallback: bool` |
| S→C | `cut` | `seq`, `from`, `to`, `url?` (absent for a crossfade), `durationMs`, `kind: "generated" \| "crossfade"` |
| S→C | `patch` | `seq`, `content[]` diffs (for `stay`), or `layers[]` (generated asset replacing a fallback) |
| S→C | `prefetch` | `assets: [{url, kind, forEdge}]` |
| S→C | `error` | `code`, `message`, `recoverable` |
| C→S | `event` | `seq`, `render` (the `seq` of the render it was made against), `component`, `type`, `value?`, `values?` (committed form values on submit) |
| C→S | `resize` | `viewport: {w, h, dpr}` |
| C→S | `reroll` | `frame?` (debug and authoring only; disabled in production by default) |
| C↔S | `ping` / `pong` | — |

`seq` is monotonic per direction. The player ignores a `render` older than the last one it applied.
The engine drops an `event` whose `render` is not the latest render it sent, so a click made just
before a transition can never fire a same-named component on the next frame.
Every message is validated against a Zod schema on both ends; the schemas live in `@videotape/core`
so the engine and the player cannot drift.

## 10. Data, security, privacy

- **Facts are never generated.** Text, numbers, images, and inputs come from the spec and the reel's
  data, rendered on the content layer. Scene prompts never contain reel data (§5.5).
- **Interactivity comes only from the spec.** The engine validates every `event` against the current
  frame: the component exists, the event is allowed for its kind, the value matches the kind (type,
  length at most 4 KB). Anything else is dropped and logged.
- **Commit policy.** Input values travel with the `submit` event by default. `commit: "change"` is
  opt-in per component for live validation.
- **Secrets.** `type: "secret"` values are delivered to the handler once, never logged, never stored
  in the reel, never patched back to the player.
- **Transport.** TLS. A session token issued in `welcome`, presented in `hello.resume`. No cookies
  in v1.
- **Assets** are content-addressed and contain no user data by construction, so they can be public
  and CDN-cached.
- **Player CSP:** `default-src 'self'`, media and images from the asset origin, no inline scripts.
- **Handlers** are the app's code and run with the app's privileges; the framework does not sandbox
  them in v1.

## 11. Developer workflow and CLI

```bash
videotape dev ./apps/site              # engine with watch + reload, opens the player; renderer: flat
videotape dev --renderers still,cut    # enable generative renderers (needs backend keys in env)
videotape check                        # validation (§5.6); exit code 1 on errors
videotape graph --format mermaid       # the app's journey graph
videotape render --viewports phone,desktop --renderers still,cut   # ahead-of-time render into the cache
videotape serve                        # production engine with a warm cache
```

`videotape.config.ts` declares the app entry (tapes and entry tape), services to inject into
handlers, style packs, enabled renderers and their options, cache location, and viewport class
overrides. Backend credentials come from environment variables, never from the config file.

## 12. Repository, stack, conventions

```
videotape/
├─ packages/
│  ├─ core/                 model, Zod schemas → JSON Schema, validation, graph, layout engine. Pure.
│  ├─ engine/               sessions, pipeline, cache, VTP server, renderer host
│  ├─ player/               browser client (vanilla TS, Vite)
│  ├─ cli/                  bin: videotape
│  └─ renderers/
│     ├─ flat/              @resvg/resvg-js rasteriser (reference renderer)
│     ├─ still-fal/         hosted image generation
│     ├─ still-comfy/       local ComfyUI image generation
│     ├─ cut-fal/           hosted first-last-frame video
│     ├─ cut-comfy/         local first-last-frame video
│     └─ live-decart/       (stretch) real-time video-to-video over WebRTC
├─ apps/
│  ├─ site/                 the demo: landing, docs, login, dashboard, report, "tube"
│  └─ desktop/              (optional) Tauri shell that opens the site full-window
├─ examples/
│  └─ hello-tape/           the smallest possible app
├─ docs/
├─ package.json             pnpm workspaces
└─ LICENSE
```

**Stack and reasons.** TypeScript strict everywhere, one language for authoring, engine, and
player. pnpm workspaces. Zod for schemas, exported as JSON Schema for other languages later. Hono
for HTTP and WebSocket (runs on Node, Bun, and edge runtimes). Vite for the player. Vitest for unit
tests, Playwright for end-to-end against the `flat` renderer. `@resvg/resvg-js` for SVG rasterising
and `sharp` for compositing and image checks. No Python in v1; local model backends are reached over
ComfyUI's HTTP API.

**Naming.** The npm package `videotape` is already taken by an unrelated, inactive package. All
packages publish under the free `@videotape/*` scope; the CLI's bin name is still `videotape`,
since bin names do not collide with package names.

**Licence.** Apache-2.0 (patent grant, standard in the model ecosystem). Model weight licences are
recorded per backend in [03-landscape.md](03-landscape.md).

**Conventions.** Conventional commits. Every package has a README with its contract. Renderers
never import each other. Nothing outside `renderers/` imports a vendor SDK.

## 13. Milestones

Order matters more than dates. Each milestone ends in something runnable.

### M0 — Foundations (`core`, `cli`)
- Tape model, Zod schemas, JSON Schema export, TypeScript authoring API.
- Validation and graph (`videotape check`, `videotape graph`).
- Layout engine: three viewport classes × seven archetypes; wireframe JSON and SVG.
- Unit tests; SVG snapshot tests for the demo's frames at every class.
- **Exit:** the demo app's tapes validate; wireframe snapshots exist for every frame × class.

### M1 — The loop with the AI off (`engine`, `player`, `renderer-flat`, `apps/site`)
- VTP server and client, sessions, pipeline with `flat` only, content layer, cuts as crossfade.
- Demo app navigable end to end at phone, tablet, desktop.
- Playwright walks every edge of the demo graph in CI.
- **Exit:** a tester signs in with the fake auth and reads a report on a phone-sized window and a
  desktop window, with keyboard only and with a screen reader.

### M2 — Generated stills (`renderer-still-*`, cache)
- Layout-conditioned scene generation via fal, then ComfyUI; style packs; validation and re-roll;
  content-addressed cache; `videotape render` ahead-of-time.
- **Exit:** landing, login, and dashboard scenes are generated; text is crisp; fields stay where the
  wireframe put them across reloads; second-session cache hit rate at or above 90 %.

### M3 — Motion (`renderer-cut-*`, prefetch, budgets)
- First-last-frame cuts along edges; prefetch; budgets and crossfade fallback; optional ambient loops.
- **Exit:** pressing "Sign in" plays a generated cut into the dashboard within 300 ms when prefetched;
  the HUD reports fallback rate.

### M4 — Ship
- Deploy the demo; docs written as a tape; the "tube" sample app; README, CONTRIBUTING, LICENSE;
  optional Tauri shell.
- **Exit:** public URL; a stranger defines a tape from the README and sees it.

### How to parallelise
`core` first, contract-first: write the Zod schemas for the tape model and for VTP messages before
anything else. After M0, `engine`, `player`, and `renderer-flat` can be built in parallel against
those schemas. After M1, `still` and `cut` renderers are independent of each other. The demo app can
be written against `core` from day one and grows with each milestone.

### After v1
`live` renderer over WebRTC (Decart Realtime API first, then self-hosted Matrix-Game or
StreamDiffusionV2 class models); server-side burn-in of facts for true video output; pinned renders
and a curation workflow; Studio (visual tape editor); Figma-style per-device frames on top of the
layout model; native players; i18n and RTL; local generation.
