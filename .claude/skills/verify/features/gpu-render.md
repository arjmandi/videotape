# GPU render

`videotape render --story <name> --model wan2.2-5b --takes 3`, run in a project, makes Wan 2.2 draw every pixel of the tape, which needs one H100-class CUDA GPU. Wan2.2-TI2V-5B draws each state's key from its own prompt, and Wan2.2-Fun-5B-InP draws each move between the two kept keys it is pinned to. Qwen3-VL-8B and Claude read the keys, so the script needs `ANTHROPIC_API_KEY` in the environment too, gives it to the pod and never prints it, and the pod's render runs under the same `--cap-usd` for its reads, so a session spends at most the cap twice: once on the pod's hours and once on reads. `scripts/runpod-render --story <name> --takes 3 --cap-usd <n>`, run in the project like every videotape command, rents that GPU on Runpod, copies the repo and the story's cached tape there, renders the app in that story, copies the tape back, appends the take lines the pod's render wrote to the project's `ledger.jsonl`, deletes the pod, and appends a pod line that names the tape. The tape is `tapes/<name>` in the project, and `--out <tape>` renders into another one. `--dry-run` prints the whole plan and creates nothing. Before it reads an API key or calls Runpod, the dry run included, it runs `videotape plan --story <name> --model wan2.2-5b` in the project through `uv`, and stops with exit 2 and that plan's error lines on stderr, so a plan the pod's render would refuse never rents a pod. On a Mac, `--model wan2.2-5b` stops with an `error:` line before writing anything.

No paid run has been made since the screenplay changed, and none in a story. A plan with a variant, a scene's second or later state, stops `videotape plan --model wan2.2-5b` and a render on wan2.2-5b with `VT111`, since Wan 2.2 films no key from another key's picture and a render draws every variant from its base's picture. The cafe and Contrail both have variants, so the script stops on them with `VT111` on this Mac before it calls Runpod, and their paid journeys below stop there until Wan 2.2 gets a first-frame mode. Only an app whose scenes have one state each, such as the starter, renders on the pod, so the dry runs below run in a starter project made in the run folder. The dry runs, the refusals and the local errors below were driven. The paid journeys are recipes whose expected lines come from the code and from the prototype 1 runs, so correct them on the first paid run.

## Sub-features

- `gpu-variants` refuses Contrail, whose 47 variants wan2.2-5b cannot draw, with the `VT111` lines `videotape render` prints and exit 2, with no key and with or without `--dry-run`, before it makes an SSH key or calls Runpod.
- `gpu-dry-run` prints the plan for the starter in its story without a key or a pod: project, story and tape, GPU, price, cap, self-destruct deadline, image, disk, env names, create body, start command, setup and render commands. Exit 0, last line `dry run: nothing was created.`
- `gpu-dry-run-out` prints the plan for another tape with `--out`, for an `NVIDIA H200` at the price `--usd-per-hour` names.
- `gpu-cap-too-small` refuses a cap too small to render after the teardown margin with `error:` and exit 2.
- `gpu-no-key` refuses a real run without `RUNPOD_API_KEY` with `error:` and exit 2, and refuses to run outside a project, in a story the project does not have, or without `uv` on `PATH`.
- `gpu-local` rejects `--model wan2.2-5b` on this Mac with `error VT111 wan2.2-5b: needs a CUDA GPU with about 80 GB, and this machine has Apple silicon (MPS) only` over `fix: render with wan2.2-5b on a CUDA GPU with about 80 GB, as scripts/runpod-render does, or with another model, as in videotape render --story starter --model stand-in`, exit 1, and writes nothing. Without the wan extra the first line is `error VT111 wan2.2-5b: needs videotape's wan extra, which is not installed here` instead, over the same fix.
- `gpu-requests` builds each Wan 2.2 request from the shot alone and builds the pod's scripts and ledger lines, proven by `uv run pytest tests/test_wan.py tests/test_runpod_render.py`.
- `gpu-smoke` is the first paid run: the cafe fixture in its story, `chalk`, with one take per shot, which draws five text-to-video keys and then six first-and-last-frame moves. Costs money. Today it stops with `VT111` before any call to Runpod, since two of the cafe's keys are variants.
- `gpu-full` is the paid Contrail run in one story, 58 keys and 102 moves. At three takes it is 160 to 480 takes, and a second story is as many again. Costs money, and far more than the smoke.
- `gpu-ledger` records one `take` line per filmed take and one `pod` line per pod session in the project's `ledger.jsonl`, each naming its tape, and `videotape dailies` rewrites the page with that tape's totals.

## How to get to it (user POV)

- In `examples/contrail`, run `../../scripts/runpod-render --story terminal --takes 3 --cap-usd 10 --dry-run` and read why the pod would refuse its plan.
- In a project whose scenes have one state each, such as one `videotape new` made, run `<repo>/scripts/runpod-render --story starter --takes 3 --cap-usd 10 --dry-run` to read the plan.
- Export `RUNPOD_API_KEY`, then run the same command without `--dry-run`. Watch the pod id it prints, then the setup and render logs. When it ends, open the tape's `dailies.html` and play the tape in TapePlayer.
- Add `--out tape-wan2` to keep the Wan tape beside the stand-in's `tapes/terminal`. Without it the pod renders into `tapes/terminal`, whose stand-in takes stay in its cache beside Wan's.
- In `examples/contrail`, run `uv run videotape render --story terminal --model wan2.2-5b` on the Mac to see why it needs the pod.

## Gotchas

- A paid run starts billing when `pod <id> created` prints and stops when the pod is deleted. The script deletes the pod in its `finally` and confirms with a read. If it prints `NOT CONFIRMED DELETED`, open the Runpod console now.
- The pod arms a timer at boot that terminates it at the self-destruct deadline even if this Mac dies. Killing the script early still deletes the pod through its `finally`; a hard kill of the Mac does not, and then the pod runs until the deadline, which the cap paid for.
- A keyless dry run assumes $3.99/h, the secure-cloud list price read on 2026-11-09, unless `--usd-per-hour` names another price. With `RUNPOD_API_KEY` set, a dry run reads the live price and stock and still creates nothing. `error: no NVIDIA H100 80GB HBM3 with CUDA >= 13.0 in the secure cloud right now` means the catalog shows no stock. `--gpu "NVIDIA H200"` is the next option, at $5.29/h.
- A LOW stock reading in the catalog does not guarantee a pod. Twice on 2026-11-09 the H100 create failed after the plan printed, with `error: POST /pods -> 400: {"detail":"There are no longer any instances available with the requested specifications. ...` and exit 2. Nothing was created or billed. The retry that worked was `--gpu "NVIDIA H200"` at $5.29/h.
- The host CUDA floor is 13.0 because `uv.lock` pins torch 2.15.0, whose Linux wheels bundle the CUDA 13 runtime. The image's own CUDA version does not matter; the venv brings its own.
- On the pod the render runs inside the project with `uv run --project /workspace/videotape`, so it uses the repo's environment, which has the wan and qwen extras, and the project needs none of its own. `cd examples/contrail && uv run --project ../.. videotape plan` shows the same on this Mac.
- The script copies the project's tape to the pod before rendering, so cached takes render again only when a prompt, key or setting changed. A changed key re-renders only the moves that start or end on it. Delete the tape's `takes/` to force a full re-render; that costs money.
- The tape comes back in the failure path too, so a run that dies after some takes keeps them, and a rerun resumes from the cache. The pod's take lines come back with it.
- Only git-tracked files are uploaded to the pod, so `git add` a new project, data file or story before a paid run. The script only checks that the story's file exists here. `ledger.jsonl` is not tracked, so the pod's ledger holds that session's lines only, and the script appends them to the ledger here.
- Every key renders before any move, so the pod loads TI2V-5B once, then Fun-5B-InP once. The first key take and the first move take include that load in their seconds and read long.
- A plan with a variant prints `error VT111 wan2.2-5b: films no key from another key's picture, and <n> keys of the plan are drawn from the base's picture` over `fix: render with a model on fal, whose image-to-video takes one picture, as in --model gemini-omni-flash-1.2, or with the stand-in`. `videotape plan --model wan2.2-5b` prints it with exit 1, and the script prints the same lines with exit 2 before it creates a pod, so no pod is rented to find it. One function, `check_modes` in `videotape/render.py`, holds the rule for both the plan and the render. `uv run pytest tests/test_render.py -k refuses_a_model` drives the render's refusal with a stand-in that lacks the mode; on this Mac `videotape render --model wan2.2-5b` stops on the GPU refusal above first.
- Before a paid run, read `videotape plan --story <name> --model wan2.2-5b` for `VT307` warnings. Wan 2.2 reads 512 tokens of a prompt and drops the rest. Contrail's longest prompt is the key of `profile()`, which umT5's tokenizer makes 391 tokens of in `terminal` and 404 in `posters`.
- Timings measured on prototype 1's screenplay: on an H200 on 2026-11-09 a text-to-video take took 80 to 105 s and a first-and-last-frame take 80 to 110 s, each including the checkpoint load on its first take. The surf shop's thirty takes ran on an H100 SXM on 2026-11-10: pod `n6lc3mo0get3jw`, 3141 s, $3.48 at $3.99/h, 2727.7 GPU seconds in the ledger. From those take times, the cafe smoke's eleven takes are 15 to 20 minutes of rendering, and Contrail's 480 takes, the most at three takes, are 11 to 15 hours, $43 to $59 at $3.99/h before setup. Both estimates are inferred, not measured.
- On prototype 1's keys, Wan's lettering read back with a CER of 0.05 to 0.77 per line, so expect `fail:` lines on a Wan tape until the lettering improves. Contrail's keys hold many more lines than the surf shop's.
- SSH can take several minutes to answer after the pod shows `RUNNING`. Runs on 2026-11-09 printed 12, 48 and 78 status lines, the last one reading `RUNNING, ssh`. A small cap's deadline should leave room for that.
- A stalled rsync times out after 120 s, and the pod is still deleted.
- `ls` on this machine is aliased to a tool that prefixes icons. Use `command ls` when you assert on file names.
