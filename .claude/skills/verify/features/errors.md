# Errors

Every error videotape prints has a code, a place and a fix or next step: a mistake in a screenplay, its data or a story, everything that goes wrong in a render or a check, and every refusal of new, doctor, retake, accept, dailies, play, publish and diff. `tests/test_errors.py::test_every_error_videotape_makes_carries_a_code_a_place_and_a_fix` fails when videotape's code makes an exception that is not a `ScreenplayError` or a `RenderError`, but for a private signal its module catches and the few the test names with what reports them instead, so no `error: ` line without a code is left. `tests/test_errors.py::test_a_corrupt_file_videotape_reads_stops_the_command_with_a_code_a_place_and_a_next_step` breaks each file a command reads from a tape or its project, `tape.json`, `dailies.json` and `ledger.jsonl`, and runs every command that reads it through the installed `videotape`; it fails when one prints a traceback or exits without a code, a place and a next step. A new file videotape reads is one row in its `CORRUPT` table. `videotape plan` prints `error <code> <place>: <message>` and `fix: <what to do>` to stderr, prints nothing to stdout, and exits 1. The place is a file and line, a file, a state or a shot. `VT201` to `VT211` and `VT213` are a screenplay's and its data's, and `VT212` is a state or move that retake, accept or `shots --state` names and the plan lacks, and `VT408` an accept of a code the shot's kept take does not fail. `VT301` to `VT309` are a story's, which `videotape plan --story <name>` checks, and `VT310` is `plan --model` without a story, but for `VT305`, which `videotape publish` raises with `VT601`, `VT602` and `VT604`; see [publish.md](./publish.md). `videotape render` stops on the same error before it draws anything, and `videotape shots` before it prints a prompt. `VT401` to `VT404`, `VT406` and `VT407` are a render's: it prints `error <code> <place>: <message>` and `next: <what to run>`, where the place is the shot and its take, the shot alone when ffmpeg fails or every take is corrupt, or `before the first call`. A paid read by Claude that fails, or answers with something other than a read, is `VT401` at the shot and take it read, like a model's call. `VT405` is a tape no render finished, which retake, accept, dailies, play, publish and diff refuse. `VT410` is a `tape.json`, a `dailies.json` or a line of `ledger.jsonl` that is not JSON, placed at the file, or at the ledger's line as `ledger.jsonl:<line>`, which every command that reads it refuses before it changes anything, and a `tape.json` whose `made` block names a model videotape does not have stops retake and publish with `VT601`, whose fix lists the models it has. Every `VT4xx` and `VT5xx` error says `next:`, and every other one `fix:`, as `explain` heads them. `VT501`, `VT502`, `VT503`, `VT504`, `VT508` and `VT509` are a check's, which a render's `fail:` lines and the dailies name, and `VT505` is the layout check's, which only `scripts/variants-test` runs; see [variants-test.md](./variants-test.md). `videotape explain <code>` prints the code's long form with an example and its fix or next step. `VT211`, `VT304` and `VT307` are warnings, and the plan goes on; `render` and `shots` print them too. A folder that is no project is `VT106`, and a wrong value in `[tool.videotape]` is `VT107`, both placed at the `pyproject.toml`. `new` refuses a name with `VT108` and a folder that is not empty with `VT109`, a render with no model is `VT110`, and a machine that cannot run wan2.2-5b is `VT111`. A render without an API key its model or a reader of its eye needs is doctor's `VT104`, an eye without its extra or its GPU is doctor's `VT105`, and ffmpeg missing outside a render is doctor's `VT102`, each in doctor's words where doctor has them. `VT605` is a `videotape.lock` that is not TOML, and `VT606` a codesign or ditto that fails.

## Sub-features

- `errors-vt201` rejects a screenplay with no scenes.
- `errors-vt202` rejects a `to=` that holds the scene itself and not a state.
- `errors-vt203` reports a scene that raised, with the state and the line.
- `errors-vt204` rejects a scene that no action reaches.
- `errors-vt205` rejects a data file that is missing, or a path outside `data/`.
- `errors-vt206` rejects a record with a value of the wrong type, naming the file, the record's position and the field.
- `errors-vt207` rejects a query that names a field its records lack, and lists the fields they have.
- `errors-vt208` rejects a `get()` that matched no record.
- `errors-vt209` rejects two actions in one state with one spoken name.
- `errors-vt210` stops a plan that reaches more states than `max_states`.
- `errors-vt213` rejects a record class with a field that is not a str, an int, a date or a time, naming the class, the field and the line that loads the file.
- `errors-vt301` rejects a story with no version or no look.
- `errors-vt302` rejects a story that directs a scene the screenplay doesn't have, naming the line and the closest real scene.
- `errors-vt303` rejects a story that names an element type the screenplay doesn't use, naming the line and the closest real type.
- `errors-vt304` warns that a scene has no direction, so its keys get only the look.
- `errors-vt306` rejects a story that is not TOML, or a table entry that is not words, naming the line.
- `errors-vt307` warns that a prompt is longer than the model allows.
- `errors-vt308` rejects a story that quotes words, with a straight or a curly double quote, naming the line.
- `errors-vt309` rejects a `--story` with no file under `stories/`, listing the stories there.
- `errors-render` and `errors-checks` are the render's `VT401` to `VT404`, `VT406` and `VT407` and the checks' `VT501`, `VT502`, `VT503`, `VT504`, `VT508` and `VT509`, proven by `uv run pytest tests/test_render.py tests/test_resume.py tests/test_retake.py tests/test_checks.py tests/test_claude.py`.
- `errors-render` stops a render on the same error, with no `tapes/` and no `ledger.jsonl` written.
- `errors-explain` prints a code's long form, and rejects a code that does not exist.
- `errors-no-project` rejects a folder whose `pyproject.toml` has no `[tool.videotape]` table, with `VT106`.
- `errors-project-value` rejects a wrong value in `[tool.videotape]` with `VT107`: a screenplay that is not `module:app` or not a `vt.Screenplay`, a model videotape doesn't have, a `max_states` or `takes` that is not a whole number, a `cap_usd` that is not dollars, or a file that is not TOML, proven by `uv run pytest tests/test_errors.py -k wrong_value`.

## How to get to it (user POV)

- Run `videotape plan` in a project with one of a screenplay's mistakes above, or `videotape plan --story <name>` with one of a story's. Each has a fixture project under `tests/fixtures/errors/`.
- Run `videotape explain VT207` anywhere.

## Gotchas

- Exit code `2` with a `usage:` line means the arguments were wrong, not that the screenplay was rejected. Recheck the command.
- A place is relative to the working directory, which is the project, so `app.py:8` and `data/drinks.json:3` name files in the fixture.
- The plan stops at the first error it meets, in walk order. A state that cannot be built hides its actions, so nothing after it could be trusted. A story is checked after the screenplay, so a story's error shows only once the screenplay plans.
- A story's place is its file from the project, with the line of the key when the key is written under its `[scenes]`, `[elements]` or `[moves]` heading. `VT301` names only the file, since what it reports is missing. `VT304` names only the file too.
- `VT306`'s message quotes Python's TOML reader. Python 3.12 and 3.14 both say `Invalid value` for words without quotes. A quote that never closes is found at the end of the file, and the error names the file's last line.
- `VT307` in the `vt307` fixture comes from its own `model = "wan2.2-5b"` in `[tool.videotape]`. The plan counts tokens without a tokenizer and counts high. umT5's own tokenizer makes 641 tokens of that prompt, which is also over 512.
- A `vt3xx` fixture's story is named `neon`, except `vt309`'s, which is `glow` so that `--story neon` is `VT309`. With another name the plan stops with `error VT309 stories: no story "<name>"` and `fix: name one of the stories there, neon`.
- `VT308` names the line by the words beside the quote, since a straight quote is escaped in the file. A story whose only quote sits alone in a value names the file without a line.
- A render's `VT403` is reported and the render goes on with the shot's next seed. When every take of the shot is corrupt, it prints each take's own `VT403` lines, then stops the render with `error VT403 <shot>: every take of the shot is corrupt` over `next: render again with more takes, which films new seeds after these, as in:` and the render command with `--takes` two past the highest seed the shot tried, as a fully refused shot's next step is. A stopped render writes no `tape.json`, which a retake reads, so the next step names the render and not a retake, and run as printed it finishes the tape, as `tests/test_render.py -k every_take_corrupt` drives. A take the model refused for its content is `VT409`, as fal's HTTP 422 `content_policy_violation` is: it is reported as `error VT409 <shot> take <seed>: ... was refused for its content: HTTP 422 content_policy_violation, <categories>`, it is written beside its take as `takes/<hash>.refused.json` and counted once in the ledger as a `take` line with `"refused": true` at the model's listed price, so the cap counts it, and no later render polls or submits it again or reports it again; each shot's record lists its refused seeds under `refused`. The render goes on, as `uv run pytest tests/test_render.py -k refus` and `tests/test_fal.py -k refused` drive. A shot whose every take is refused lets the other shots film, is named with its seeds under the record's `unfilmed`, and then stops the render with `error VT409 <shot>: every take of the shot was refused for its content` and, as its next step, the render command with more takes, which films new seeds; one whose seeds are corrupt and refused stops with `VT403`. `VT401`, `VT402` and `VT404` stop it. The takes already filmed stay on disk and in the ledger, the record says `"complete": false`, and the next render resumes from them. Its failures' next step, in `dailies.json` and on the dailies page, is that render with two more takes in place of a retake, which would stop with `VT405`, as `tests/test_render.py -k stopped_renders_failures` drives. In the screen test, which has no `--takes`, a key whose every take is corrupt stops with `VT403` and a next step to delete each clip the lines above name, with the files beside it that share its name, and run the screen test again, which films those seeds anew; `tests/test_screen_test.py -k films_it_anew` follows it and the screen test finishes. A `VT401` on a request fal recorded beside its take, as `tests/test_wan3.py -k fails_for_good` drives, names that record in its next step, since only deleting it lets the render submit a new, paid take.
- `VT203`'s message quotes Python's own exception text. Python 3.12, which `.python-version` pins and `vt-verify run` uses, says `integer division or modulo by zero`. Python 3.14 says `division by zero`, so `tests/test_errors.py` takes the text from the Python it runs on.
- The `vt210` fixture sets `max_states = 5` in its `pyproject.toml`. Without that line the limit is 500.
- `vt-verify run` sets `PYTHONDONTWRITEBYTECODE=1`, so a drive leaves no `__pycache__` in a fixture. A fixture declares no dependencies, so `uv run videotape plan` typed by hand in one fails with ``error: Failed to spawn: `videotape` `` and leaves a `.venv` and a `uv.lock` there. Use `vt-verify run`.
