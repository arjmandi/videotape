# Wan 3.0 render

`videotape render --story <name> --model wan3.0 --takes 3 --out tape-wan3 --cap-usd <cap>`, run in a project, renders the app's shots in that story with Wan 3.0 on fal into another tape of the project. Each key is a call to `alibaba/wan-3.0/text-to-video`. Each move is a call to `alibaba/wan-3.0/image-to-video` whose first and last frames are pinned to the kept Wan 3.0 keys of the state it leaves and the state it lands on, so every pixel of the tape is Wan 3.0's. Every call asks for 720p, 16:9, five seconds, no audio and no prompt expansion. fal bills $0.10 a second at 720p, so a call is about $0.50. Before it films, the render prints one line with the shots, the calls from one take each up to the limit, their price, the cap and what this tape has already spent. It needs a cap, `--cap-usd N` or `cap_usd` in `[tool.videotape]`, and stops before the call that would pass it; without one it does not start. Up to two calls run at once, fal's limit for a new account. Each request is recorded beside its take as soon as fal accepts it, so a render that stops resumes by polling it, never by paying again. The key comes from `FAL_KEY` in the environment, or else the project's `.env`, and is never printed. Each call adds a line to the project's `ledger.jsonl` with its tape, its seconds, the duration fal reports and its dollars, and the take's sidecar keeps fal's raw answers. Qwen3-VL-8B reads the keys on this Mac, and Claude reads them as a service, a paid read of each take of a key under the same cap, which needs `ANTHROPIC_API_KEY` from the environment or the project's `.env`, is cached in the tape's `looks/`, and adds a `read` line to the ledger. TapePlayer plays the tape as it plays any other.

No paid run has been made since the screenplay changed, and none in a story. The missing-key error, the estimate and the tests below were driven. The paid journeys are recipes whose expected lines come from the code and from the prototype 1 run, so correct them on the first paid run.

## Sub-features

- `wan3-no-key` rejects `--model wan3.0` without `FAL_KEY` with `error VT104 .env: wan3.0 needs FAL_KEY, and it is not in the environment or .env` over `fix: copy .env.example to .env and set FAL_KEY there, or export it`, doctor's words for the same check, exit 1, before any network call and before writing anything.
- `wan3-estimate` prints the plan's estimate for Wan 3.0 with no key: `videotape plan --story <name> --model wan3.0`.
- `wan3-requests` builds each call from the shot alone, reads a recorded answer with no network, prices it, and prints the estimate line, all proven by `uv run pytest tests/test_wan3.py tests/test_fal.py`.
- `wan3-cap` refuses to start without a cap, stops at the cap, sends each request once and resumes a recorded one, proven by `uv run pytest tests/test_resume.py tests/test_wan3.py`.
- `wan3-checks` needs the qwen extra and `ANTHROPIC_API_KEY`, because Qwen3-VL-8B and Claude read every model's keys but the stand-in's, proven by `uv run pytest tests/test_qwen.py tests/test_claude.py`. Claude's reads are proven with recorded replies and no network: the request's picture and prompt, the read it parses to, the cache, the reservation under the cap, the ledger line, a missing key as `VT104` and a reply cut short.
- `wan3-paid` is the paid run into `<project>/tape-wan3`. Costs money, and waits for the user's cap.
- `wan3-cached` reruns the same command. It prints the estimate line with what the tape has spent, makes no call, and adds no ledger line.
- `wan3-ledger` records one take line per call with `tape`, `request_id`, `seconds`, `duration` and `usd`, and the tape's dailies total adds those dollars.
- `wan3-player` plays the tape in TapePlayer, whose window takes the tape's own size.

## How to get to it (user POV)

- Export `FAL_KEY`. In `examples/contrail`, run `uv run --project ../.. --extra qwen videotape render --story terminal --model wan3.0 --takes 3 --out tape-wan3 --cap-usd <cap>`. The repo's environment brings the qwen extra, which the example's own does not have.
- Then run `open clients/macos/build/TapePlayer.app --args examples/contrail/tape-wan3` from the repo root.

## Gotchas

- The key is only ever read from the environment. `vt-verify run` records the command in `.cmd` and `vt-verify exec` records its whole argv, so never pass the key as an argument to either.
- A submit is sent once and never again, because a second one could pay twice. fal's answer to each submit is recorded beside the take as `takes/<name>.request.json`, with the endpoint, the request id and its urls, before the wait. When a poll or a download fails, the render stops with `error VT401 <shot> take <seed>: ...` naming the request, and a rerun polls and downloads that request instead of submitting it again. When fal refuses the request's result for good, the same `VT401` comes back on every rerun, and its next step ends `or delete tape-wan3/takes/<name>.request.json first, and the render submits a new, paid take`. Every `VT401` on a request that was recorded carries that next step, a one-off failed poll as much as a refusal for good. A take whose clip is corrupt or gone is downloaded again from its record, which costs nothing and goes past the cap. A corrupt clip with no record is `VT403` and never filmed again; a gone clip with no record is filmed again as a new, paid take.
- Each call is reserved against the cap at its listed price, $0.50, and the ledger records what fal billed, so the spend can end a little past the cap when fal bills more than five seconds.
- A second story is a second tape with its own cache, so name it another `--out`, and expect the price of every take again. fal takes prompts of up to 20,000 characters, and Contrail's longest is 1,121.
- The estimate line counts every shot, from one take each to the limit, whether it is cached or not; only `$<spent> spent` comes from the ledger. It assumes five seconds a call, and the ledger then records the duration fal reports.
- The two key images go to fal inline as base64 PNG data URIs of about 1.3 MB each. fal's API page says file inputs accept them, and its storage page discourages them above a few KB. When fal rejects a move's request, suspect its size first.
- fal's safety checker stays on, its default, because turning it off needs account authorization.
- Qwen and Claude read the keys. Claude needs `ANTHROPIC_API_KEY` and bills for each take of a key it reads, at most $0.17 at the estimate, under the render's cap, and the estimate line counts its reads. Qwen needs the qwen extra. Without it the command stops with `VT105` before any call. Qwen loads, and on a first run downloads 17.5 GB of weights, after the first key take, so a failed download stops the render after the calls in flight, up to two, were paid for. Run `vt-verify launch qwen` and doctor first, and look for `weights cached` in its `info qwen` line.
- A Wan 3.0 tape is gitignored and exists only in the checkout that rendered it. It cost money, so never delete it, its `takes/`, or its lines in the project's `ledger.jsonl`.
- `tests/fixtures/wan3.0-text-to-video.json` and `tests/fixtures/wan3.0-image-to-video.json` hold fal's answers recorded from the paid run of 2026-11-10 on prototype 1's surf shop, as `tests/fixtures/wan3.0.txt` says. The tests read only their shape, so they stay as they are.
- `videotape/hosted.py` films wan3.0 from its `FalModel`, `WAN3`, through the adapter that also films minimax-h3 and gemini-omni-flash-1.2; see [fal-models-render.md](./fal-models-render.md). A change to the adapter is a change to all three.
- Wan 3.0's takes are never trained on.
