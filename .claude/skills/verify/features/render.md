# Render

`videotape render --story <name>`, run in an app's project, plans the app, checks the story and prints its warnings, and then renders every shot into `tapes/<name>/` in the project: a key for every state and a move for every action, each from the prompt the story gives it. It renders with the model that `[tool.videotape]` names, or the one `--model` names. A shot films one take at a time, seeds 1, 2, 3 and on, and stops at the first take that passes every check, up to `takes` in `[tool.videotape]` (4 unless set) or `--takes N`; when none passes it keeps the best of them. A key keeps the take with the most hotspots found, then the fewest invented controls, then the lowest character error, then the lowest seed, and its last frame becomes the state's key image. A move is drawn between the two kept key images it joins and keeps the take whose first and last frames sit closest to them. Shots that do not depend on each other film at once, up to the model's limit: every key first, and a move as soon as both of its keys are done; the stand-in films 8 at once. The stand-in's own reader checks the stand-in's keys: it reads every line of the key, each occurrence of a repeated line included, finds every action by its words, and lists every box whose words match none of the key's lines. The command prints one line per shot as it finishes, in the order they finish, after one estimate line for a model that bills per call, `<model>: <shots> shots, <calls> calls, $<price> at $<rate>/s, cap $<cap>, $<spent> spent`: `<n>. <shot>  kept take <seed>, passed|fails <codes>, <k> takes filmed|cached, $<cost>, <seconds> s`. Then it prints the totals, `<shots> shots, <takes> takes filmed, $<cost>, <seconds> s, tape <MB> MB -> <tape>`, and on stderr each failing shot as `fail: <n>. <shot>  <code> <about>: <evidence>` with `  next: videotape retake "<state>" --story <name>` under it, and each accepted one as `accepted: ...` with its reason. It exits 1 when a kept take fails a check nobody accepted. The tape holds `tape.json` with one scene per state (its key, its `words`, its `hotspots` and, for a state with a search bar and options, its `search`) and a `made` block that says what made the tape, one key image per state, the opening clip and one clip per move, a render-time sidecar per take, `dailies.json` (the tape's record, which also carries accepts, retake seeds, corrupt seeds and the limit on takes) and `dailies.html` for review, and a `dailies/` folder with a crop per failure the record names, and no other. Every filmed take appends a line to `ledger.jsonl` in the project, naming its tape. Run again, a render reuses every take on disk, and editing one line re-renders only its key and the moves that start or end on that key. `--out <tape>` writes another tape of the same app in the same story. A model that bills per call renders under `cap_usd` in `[tool.videotape]` or `--cap-usd N`, stops before the call that would pass it, and resumes without paying for a take twice. `videotape dailies --story <name>` rewrites the page and opens it. `videotape retake "<state>" --story <name> [--takes N]` films new takes of one shot. `videotape accept "<state>" <code> --story <name> --reason "<why>"` records a failure as accepted. `videotape play --story <name>` builds TapePlayer when it needs to and opens the tape in it.

## Sub-features

- `render-first` renders Contrail's 160 shots in a story from no `tapes/<story>/`, prints a line per shot and the totals, and exits 0 with nothing on stderr. Every shot passes by its third take.
- `render-cached` reruns with no model calls. Every shot prints `cached`, and `tape.json` and the keys stay byte-identical.
- `render-outputs` writes `tape.json` with each state's `words`, `hotspots` and `search`, `keys/<state>.png`, `moves/opening.mp4` and `moves/<state>--<words>.mp4` as H.264 yuv420p clips at 1280x704 and 24 fps, and a `takes/<hash>.json` sidecar with each take's render seconds and GPU.
- `render-ledger` appends one line per filmed take to `ledger.jsonl` in the project, each with `"tape": "tapes/<story>"`, and `videotape dailies --story <story>` rewrites the page with that tape's totals and opens it.
- `render-dailies` writes `dailies.json` and `dailies.html`. The page opens with the summary and the first-take yield, a Failures section when a kept take fails (grouped by code, each with its evidence, a crop and its next steps), a Keys section that shows the kept keys side by side, then each shot's takes with the kept one, each take's checks by code, seconds and cache status.
- `render-cafe` renders the cafe fixture's 11 shots in its story, `chalk`.
- `render-cascade` re-renders the key of the edited state and the moves that start or end on that key, and nothing else.
- `render-out` renders with `--out tape-b` into that folder, leaves `tapes/chalk/` byte for byte as it was, and names `tape-b` in its ledger lines, so each tape's dailies total only its own takes.
- `render-takes` renders one take per shot with `--takes 1`, exits 1 with `fail:` lines and their retake commands for the shots whose only take carries a stand-in flaw, writes the Failures section, and rejects `--takes 0` with a usage error.
- `render-retake` films a new take of a failing shot with the next seed, keeps it when it passes, redraws the moves pinned to the changed key, and a later plain render keeps it.
- `render-accept` records a failing check as accepted with a reason, shows it as accepted in the dailies, and the next render exits 0 and lists it; a check that is not failing is refused.
- `render-hotspots` lists a hotspot in `tape.json` only for an action the checks found on the kept key. A move whose action was not found still renders and is listed under `moves`, and `render` prints a `fail:` line for the hotspot and exits 1.
- `render-cap` prints the estimate with the cap and what the tape has spent, stops a model that bills per call before the call that would pass the cap, says what was spent, resumes with a higher cap, and pays for each take once; without a cap it does not start. Proven by `uv run pytest tests/test_resume.py`. The cap is checked against each call's listed price, and the ledger records what the call then billed.
- `render-play` builds TapePlayer when it is missing or stale and opens the tape. Proven by `uv run pytest tests/test_play.py` with the launcher injected; never drive it.
- `render-model` rejects an unknown `--model` with a usage error, and a render without `--story` with another. `--model wan2.2-5b` is covered in [gpu-render.md](./gpu-render.md) and `--model wan3.0` in [wan3-render.md](./wan3-render.md).

## How to get to it (user POV)

- In `examples/contrail`, run `uv run videotape render --story terminal`, then `uv run videotape dailies --story terminal` to open `tapes/terminal/dailies.html`, and `uv run videotape play --story terminal` to click through the tape. Run `uv run videotape render --story posters` for the other look.
- Read a `fail:` line's `next:` and run it: `uv run videotape retake "flight(CT 104, 2026-12-13)" --story terminal --takes 2`. Or accept it: `uv run videotape accept "booked(CT 300, 2026-12-11)" VT503 --story terminal --reason "a printed logo, not a control"`.
- Edit a line of a screenplay, a value in its data or a line of the story, and run the same render again.
- Add `--out tape-<name>` to keep a second tape of the same app and story beside the first.
- Set `takes = 2` or `cap_usd = 20` in `[tool.videotape]`, or pass `--takes 2` or `--cap-usd 20`.

## Gotchas

- A key take's cache key is the shot's mode, the prompt, the model name, the seed and, for a model that has them, its generation settings. A move take's cache key also holds the two key images it is pinned to, which is what makes a changed key re-render only its moves. The prompt holds the story's words, so a change to the story changes the cache key of every shot whose prompt it reaches. The cache is not keyed on the stand-in's code. After changing how the stand-in draws or encodes, delete the tape's `takes/` (or the whole tape) before rendering, or old takes come back from cache.
- Shot lines come in the order the shots finish, which differs from run to run with eight workers. Sort them by number before comparing, and strip the time at the end, which also differs.
- A shot stops at the first take that passes, so `kept take 3, 3 takes filmed` means seeds 1 and 2 failed. The stand-in's seeds 1 and 2 may carry a flaw and seed 3 is always clean, so a shot never films a fourth take and an exit of `1` with `fail:` lines from a default render is a regression.
- `--takes` changes how many seeds a shot may try, not the cache key, so `--takes 1` on a tape rendered with the default keeps only seed 1 per shot. When that changes a kept key, the moves that start or end on it re-render. The record remembers the limit a tape was rendered with, in `"takes"`, and `retake` renders with that limit.
- A model that bills per call reserves each call at its listed price before submitting it, and the ledger records what the call then billed, which fal reports as the clip's duration. The `VT402` line says so, `at the listed price of $0.50 a call`. A call that fails after its submit keeps its reservation, since fal may have billed it, and the render stops on it. A request's ledger line is written once, so a take whose clip was deleted is downloaded again from the request record beside it, under any cap, and counts as `cached`.
- Two shots that share a take name, as two states that show the same words do, film it once: the second waits for the first and reads the take as `cached`.
- `ledger.jsonl` is append-only and lives in the project, not in the tape. A render appends a line per take it films; a cached run appends nothing. Deleting a stand-in tape leaves its lines behind, and a new render of that tape adds to them, so its totals then count both. For a model that bills per call, the sum of the tape's lines is what the cap counts, so deleting a tape does not reset what it spent.
- Kept take numbers come from the stand-in's flaws, which are derived from a hash of the prompt and seed. A prompt change, such as a new line in a scene, changes them. Re-run the journey and update the expected lines rather than treating that as a regression.
- `render-first` needs no `tapes/<story>/`. If one exists, every line says `cached` and the totals say `0 takes filmed`.
- Each story has its own tape and its own take cache, so rendering `posters` after `terminal` films every take again.
- `render-cached` keeps `tape.json` byte for byte only while videotape's own code is unchanged, because its `made` block holds a hash of that code.
- A state's key and clips are named by its name in lower case with every run of other characters turned into a hyphen, so `results(SEA, 2026-12-12)` has `keys/results-sea-2026-12-12.png`. A move is named by its state and the words its action is found by.
- The stand-in draws each line as a box in rows of 33 pixels, 15 rows to a frame. A row is what the prompt lists between two semicolons, or one element's words when it has none, so each option of a search bar and each row of a list is a row. Its extra-box flaw adds one more row, `Not in the script`, which is the invented control the checks fail with `VT503`. A state with more rows stops the render with `error VT401 key <state> take <seed>: the stand-in has no room to draw "<line>"`.
- The totals print the tape path relative to the project, so it is `tapes/chalk` or `tape-b`. A `next:` command under a `fail:` line adds `--out tape-b` for a tape that `--out` named.
- `videotape dailies` opens the page with the default browser unless `BROWSER=true` is exported. `vt-verify run` passes the environment through, so export it before the drive.
- In a tall capture every take is near the window at once, and a take that has not decoded yet shows black or its first frame. Read the checks and badges, not the pictures. In a browser only the takes near the window load.
- `ls` on this machine is aliased to a tool that prefixes icons. Use `command ls` when you assert on file names.
